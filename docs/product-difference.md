# 与上游 DSH 桌面端的产品差异（一页纸）

> 用途：PLAN M0 交付物之一，回答"如果上游已经有桌面端，我们为什么还要做"。
> 状态：**假设草案**——本机安装的 `@deepseek-ai/dsh-desktop-runtime@0.2.1-rc.3` 已包含 `dsh-desktop-host` 与 `desktop-runtime.json`，但本次无法联网核对上游桌面的实际能力，因此下列"上游现状"均为**待核实假设**，核实方式写在第三列。

## 1. 四个候选差异

| # | 我们的主张 | 上游现状（待核实） | 怎么核实 |
|---|---|---|---|
| D1 | **原生渲染**：GPUI 原生多面板、原生终端、GPU 虚拟化，而不是 WebView 承载 | 上游桌面宿主大概率仍以 Web 前端为主（存在 `web-frontend`、`host-webserver` 包） | 装上游桌面端，测 10k 事件滚动、终端吞吐、冷启动 |
| D2 | **Agent Runtime 用 Rust 拥有**，Node 只作为插件兼容层 | 上游运行时是 Node + Cordis，Agent Loop 在 Node 内 | 读上游包结构，确认 Agent Loop 所在进程；测崩溃恢复 |
| D3 | **插件平台有稳定公开契约**（CPP-v1 + ADC-v1），第三方可不读主程序源码接入 | 上游插件契约绑定 Cordis/React 内部结构 | 取一个上游社区插件，评估其升级时的破坏面 |
| D4 | **外部 Agent/工具一等公民**（ACP/MCP 与内置工具同权，进同一 Policy 与审计） | 上游有 ACP/MCP 包，但可能作为扩展而非核心边界 | 对比 MCP 工具与内置工具的审批/审计路径是否一致 |

## 2. 我们不主张的差异（避免自欺）

- **不是**"支持 DSH 插件"——上游天然支持，我们只是兼容。
- **不是**"界面更好看"——美观不是护城河，且不可验证。
- **不是**"更多模型"——这是配置问题，不是产品差异。

## 3. 如果差异不成立会怎样

| 情形 | 判定 | 动作 |
|---|---|---|
| D1 不成立（原生没有可感差异） | 判死实验 A 失败 | 转 ADR-0005 的 C 方案（Tauri + Web UI） |
| D2 不成立（Rust 运行时没有可靠性/性能优势） | M2 后评估 | 保留 Rust 核心但降低投入，转向插件平台 |
| D3 不成立（第三方其实不需要稳定契约） | M3 退出条件失败 | 收缩 ADC-v1，只做内建 UI |
| D4 不成立（ACP/MCP 并非刚需） | M2 后评估 | 降级为普通插件 |

## 4. 结论

当前最重要的不是论证这四点**成立**，而是用 M1 的三个判死实验证伪其中任何一点。**D1 必须最先验证**——它是四条里唯一"不成立就换架构"的。
